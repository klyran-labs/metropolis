# @agentguard/gateway

The real x402 / AP2 payment gateway. This is the service `docker/Dockerfile.gateway`
now actually builds and runs — previously that container's runtime was a one-line
inline stub that always returned HTTP 402 and never touched signatures, policy, or
Monad (see `docs/GAP_ANALYSIS.md`, finding 1.4).

## What it does

1. `GET /v1/inference` with no `Payment-Signature` header → issues a real x402
   challenge (`createX402Challenge`).
2. Same request with a `Payment-Signature: x402 <base64>` header (as produced by
   `@agentguard/x402-middleware`'s `encodeX402Authorization`) →
   - rejects if the request targets a different merchant than this gateway's own
     configured `GATEWAY_MERCHANT_ADDRESS`,
   - rejects if the EIP-712 signature doesn't recover to `request.agent`,
   - pre-flight simulates against `PolicyEngine.evaluate` (a free view call — a
     policy deny is caught here before any gas is spent),
   - if allowed and a relayer key is configured, submits
     `AgentWalletGuard.executeGatedPayment` and waits for the receipt.

## Why this isn't a registered npm workspace

This package deliberately is **not** added to the root `package.json`
`workspaces` array, and its `dependencies` are documentation, not something
`npm ci` resolves for it. Reason: this repository's `package-lock.json` can
only be regenerated by running `npm install`, and doing that requires registry
access this environment didn't have when the gateway was built (see
`docs/GAP_ANALYSIS.md`). Adding a new workspace without a matching lockfile
entry breaks `npm ci` everywhere it runs — CI, Docker, and any contributor's
`npm ci` — regardless of *their* network access, because `npm ci` refuses to
resolve anything; it only installs exactly what the lockfile already says.

Instead, this package is built directly against the already-hoisted
dependency tree at the repo root: `@agentguard/shared-types` and
`@agentguard/x402-middleware` are already symlinked into root `node_modules/@agentguard/`
(they're existing, already-locked workspaces), and `viem` is already hoisted
there too (it's a dependency of `apps/web` and `packages/x402-middleware`).
Node's module resolution walks up from `services/gateway/dist/` to find them
without needing this directory to be a declared workspace. Build with the
already-installed root TypeScript compiler:

```bash
# from repo root
npx tsc -p services/gateway/tsconfig.json
node services/gateway/dist/index.js
```

**Follow-up, once a real `npm install` can be run:** add `services/*` to the
root `workspaces` array, regenerate `package-lock.json`, and this package's
`dependencies` become real, installed dependencies instead of documentation.

## Configuration

| Env var | Required | Description |
|---|---|---|
| `PORT` | no (default 8080) | HTTP listen port |
| `MONAD_CHAIN_ID` | no (default 10143) | Chain ID |
| `MONAD_RPC_URL` | no (default testnet) | Monad JSON-RPC endpoint |
| `POLICY_ENGINE_ADDRESS` | yes | Deployed `PolicyEngine` address |
| `REPUTATION_REGISTRY_ADDRESS` | yes | Deployed `ReputationRegistry` address |
| `AGENT_WALLET_GUARD_ADDRESS` | yes | Deployed `AgentWalletGuard` address (also the EIP-712 `verifyingContract`) |
| `USDC_TOKEN_ADDRESS` | yes | ERC-20 token settled by default |
| `GATEWAY_MERCHANT_ADDRESS` | yes | This gateway's own payee address |
| `GATEWAY_RELAYER_PRIVATE_KEY` | no | If unset, the gateway still issues challenges and simulates policy decisions but returns `503` instead of submitting a settlement transaction |

## Testing

`test/gateway.test.mjs` covers what's verifiable without a live chain: challenge
issuance shape, and rejection paths that fail before any RPC call (merchant
mismatch, missing/invalid signature). It intentionally does **not** test a
successful on-chain settlement — that needs a running Monad node (or `anvil`),
which wasn't available in the environment this was built in. Run against a
local `anvil` fork with real deployed contracts to verify that path before
relying on it in production.
